# netparse 最终方案

> **一句话**：把网络设备**配置文件**解析成结构化 JSON，产出**接口台账**与**端口状态**两张表。
> **定位**：只覆盖**配置面**（设备上写下来的东西），不覆盖硬件/运行态——那些交给 NETCONF / SNMP / 命令输出那条线。
> **状态**：语法与语义已定稿；引擎已规整为 Python 库；华为模板已交付（接口块内覆盖率 **100%**，
> 318 台实测）+ 中兴模板已交付（64 台实测）+ 字段级 transform（`func=`，接口类型已实战 100%）。

## 0. 一页速读

**这是什么**：一套模板 DSL（`.cmdb`）+ 嵌套状态栈引擎，把厂商配置解析成 JSON。

**不是什么**：
- ❌ 不是通用 CMDB 采集器（硬件槽位、光模块、License、MAC 表、在线状态**配置里没有**，解析不出来）
- ⚠️ "三厂商已验证"要拆开说：华为已交付（318 台验证 / 接口块内 100%）；中兴已交付
  （2026-11-21，`zte-m6000.cmdb`，64 台实测 0 失败 / 0 密文泄漏）；诺基亚仍只有 6 台样本（未交付）
- ❌ 不是"缩进解析器"（**运行期完全不使用配置文件的缩进**，见 3.3）

**现状硬数据**

| | incumbent（既有 Python+TextFSM 管线） | netparse（当前） |
|---|---|---|
| 台账列覆盖 | **19 / 19** | **9 / 19** |
| 规模验证 | 8440 文件 / 627 万接口 / **0 失败** | 318 台 / 166 万接口块内命令行，接口块内覆盖率 **100%**；回归基线 2 fixture / 14 记录 |
| 交付模板 | 华为 1 份 | 华为 15 集合 + 诺基亚（诺基亚仅 1 个集合） |
| 跨厂商 | 华为 | 华为 + 诺基亚（未交付） |

**结论**：方案成立，但**成立的部分比它宣称的要多、宣称的顺序比实际的错位**。
它真正的价值不是"做一个通用配置解析引擎"，而是**把"块边界"从代码搬进模板**——
incumbent 自己的注释写着：*"这一步是全部方案的地基——块边界必须 100% 确定，否则空块会吸附后续段落、字段会串到隔壁接口"*。

## 1. 方案定位与适用边界

### 1.1 覆盖什么（配置面）

真实交付物是两张表，全部来自配置：

**① 接口台账**（`build_excel.py:104-125` 定义 19 列）—— 一行一接口，1:N 的关系折进列里。

**② 端口状态**（5 列：设备名称 / 管理IP / 采集时间 / 接口名称 / 配置状态，23.9 万行/月）。

这两张表**完全来自配置**，不需要任何命令输出或 SNMP。

### 1.2 不覆盖什么（明确出界）

| 出界项 | 需要什么 | 建议走哪条线 |
|---|---|---|
| 板卡 / 接口卡 / 光模块 / 电源 / 风扇 | `display device` / 实体设备台账 | ntc-templates / pyATS Genie |
| License / 软件版本明细 | `display license` | 同上 |
| CPU / 内存 / 温度 / 在线状态 | SNMP / 遥测 | SNMP |
| MAC 地址表 | `display mac` | ntc-templates |
| 运行态路由 / BGP 会话状态 | NETCONF-RPC / `display bgp peer` | NETCONF |
| 跨设备拓扑 / 光纤配线 | 多设备关联 + 资产台账 | CMDB 侧 |

> **文档应该写清"本工具只覆盖配置面"**，并把出界部分明确指向 ntc-templates / NAPALM / NETCONF，
> 而不是含糊地说"入 CMDB"。

### 1.3 与现成方案的对比

**先摆事实**：这个项目**不是第一版方案**。既有管线已经试过两条路——
`huawei_vrp.fsm`（TextFSM 模板，文件头 36 行踩坑笔记）与 `parse_huawei_vrp.py`（41KB 纯 Python 切块 + 整形），
两条路都在生产跑了 8440 文件 / 0 失败。**netparse 是第三版。**

| 维度 | **netparse（DSL+栈）** | TextFSM | ntc-templates | pyATS Genie | Batfish | TTP | 直接写 Python | NETCONF/YANG |
|---|---|---|---|---|---|---|---|---|
| ① 跨厂商增量成本 | **低**：一份模板/厂商，块边界写在模板里 | 中：无嵌套状态，块边界靠外层代码切 | 高：按 (platform, command) 建，**只覆盖命令输出** | 高（思科为主） | 极高（Java+Docker） | 中（模板可嵌套，语法是 Python） | 高：41KB 只覆盖华为一个厂商 | 低，但每厂商要装 YANG，老设备不支持 |
| ② 模板可读性（网络工程师能自己写吗） | **高**：像配置本身 | 中：正则味重，缩进会被转成 `[ \t]+` | 低（用户不写） | 低（Python 类） | 无 | 中：Jinja2 风格，但**标签里是 Python 代码** | 无模板 | 无模板 |
| ③ CMDB 入库适配度 | 中：输出 JSON，资产层另做 | 低（扁平 list of dict） | 低 | 低 | 高但输出是"行为"不是台账 | 中 | **高**：已直接产出 19 列 xlsx | 高 |
| ④ 长期维护成本 | 低-中：新命令=加一条规则，新厂商=一份模板 | 中 | **低**（社区 400+ 模板） | 低 | 中 | 中 | **高** | 低（设备侧成本高） |
| ⑤ 生态复用度 | **零**（自造 DSL） | 高（ntc-templates 底座） | 高 | 高 | 高 | 中 | n/a | 高 |
| ⑥ 调试与质量保障 | **弱**：回归 14 条 + 325 项断言，无样例库，无 CI（较评审时已有改善，但与 ntc-templates 的样例库差距仍大） | 强：`.raw`+`.yml` 成对样例 + 三重断言 | 强 | 强 | 强 | 中 | 强：5 个校验脚本 | n/a |

**逐维度结论**：
- ① **netparse 赢**，但前提是"一份模板一个厂商"**只在华为身上被验证过**
- ② **netparse 赢**，且这是相对 TextFSM/TTP 的**真优势**（TTP 的缩进语义有坑，incumbent 笔记里已记）
- ③ **netparse 输，且是结构性输**——资产层已经存在，只是不在这个仓库里
- ④ **netparse 赢**，前提是模板语法稳定 + 有质量保障
- ⑤ **netparse 输得最彻底**：自造 DSL = 无外部贡献、无样例库生态、无 CI 模板、除了作者没人会写
- ⑥ **netparse 输得最厉害**，也是当下最该补的

**判断：不是重复造轮子，但"更易读一点"值不值得自己造，取决于一个尚未验证的假设**——
「网络工程师（不是 Python 工程师）能自己写/改模板」。
这个假设目前**零证据**，验证方法见 8.3。

**netparse 唯一无可替代的价值**：

> 把 incumbent 第 1 层（`split_interface_blocks` / `split_qos_profile_blocks` / `split_route_static` / `split_device_level`
> 四个纯 Python 切块函数）**从代码变成模板声明**。

## 2. 模板语法（概览）

**完整语法与场景手册见 `TEMPLATE-GUIDE.md`。**

### 2.1 结构

集合用**缩进表达层级**（注意：**这是模板自己的缩进**，与被解析文件无关，见 3.3），
每层是独立状态，有自己的 `start`（进入）/ `end`（退出）/ `[value]`（字段）/ `[rule]`（规则）。

```text
Interfaces type(list) start(^interface\s+) desc(接口集合)
[value]
Name        type(str)  reg(\S+) desc(接口名) option(Key)
Description type(str)  reg(.+)  desc(描述)
Statistic   type(dict) desc(流量统计)
  Enable type(bool) desc(统计开关)
[rule]
^interface\s+${Name}
^\s*description\s+${Description}\s*$
^\s*shutdown\s*$                   -> AdminStatus=down

  IpAddress type(list) start(^\s*ip(v6)? address) desc(接口IP)
  [value]
  Address type(str) reg([^/\s]+) desc(地址)
  [rule]
  ^\s*ip address\s+${Address}\s+${Mask}\s*$  -> Family="ipv4"
```

### 2.2 集合声明选项

| 选项 | 形式 | 含义 | 省略时 |
|---|---|---|---|
| `type` | `type(list\|dict\|str\|int\|float\|bool)` | 集合类型 | **list** |
| `start` | `start(<正则>)` | **进入**该层的触发器 | 栈底常驻，始终生效 |
| `end` | `end(<正则>)` | **离开**该层的触发器 | **不启用 end 匹配** |
| `desc` | `desc(<说明>)` | 中文说明 | 无 |

> `Key` / `Required` **不在集合上声明**，写在字段的 `option(...)` 里（见 2.3）。
> 集合级 `Key(...)` / `Required(...)` 已废弃，lint 报错。

### 2.3 字段声明与规则写法

```text
<字段名> type(<类型>) [option(Required Key)] [default(<值>)] [reg(<正则>)]
           [inherit=<集合>.<字段>] [desc(<说明>)]
```

| 选项 | 含义 |
|---|---|
| `option(Key)` | 该字段参与**聚合键**（同键的子记录合并成一个对象） |
| `option(Required)` | 该字段必填，缺失则该记录无效（丢弃） |
| `default(<值>)` | 未命中时的默认值 |
| `reg(<正则>)` | 该字段的匹配正则，供 `${字段}` 引用 |
| `inherit=<集合>.<字段>` | 继承该集合该字段**上次**匹配到的值（注意：不是"所属父"） |

规则段里**一行就是一条正则**。`${字段}` 插入该字段 `reg()` 里的正则并命名成捕获组（TextFSM 风格）；
`${A.B}` 引用嵌套字段。

**`->` 目标的四种落点**：

| 写法 | 落在哪 | 写什么 |
|---|---|---|
| 省略 `->` | 当前集合·当前记录 | 全部捕获组 |
| `-> 字段[=常量]` | 当前集合·当前记录 | 全部捕获组 **+** 该字段 |
| `-> 路径.字段[=常量]` | 当前记录内的嵌套 dict | **只写**该路径 |
| `-> 集合名{字段1,字段2}` | 指定集合（跨集合时用） | 只写花括号里列出的字段 |

> ⚠️ 同一条规则里**不能混用** `${X}` 与 `(?P<X>...)`——会触发 `redefinition of group name` 崩溃。
> 裸命名组（`(?P<X>...)`）**不会**把 `X__Y` 还原成嵌套路径 `X.Y`，写嵌套字段请用 `${X.Y}`。

## 3. 运行语义（嵌套状态栈）

### 3.1 逐行处理

```
① 找命中的 start（从栈顶向下）：
     每层先看自己的 start，再看它的子集合的 start；
     最后看尚未激活的顶层集合的 start
     命中集合 L：
       · L 是栈上某层      → 存档 L 及其所有子层的记录，L 以下出栈，L 开新记录
       · L 是某层的子集合  → 压入 L（父层记录继续累积）
       · L 是未激活的顶层  → 压入 L
     用 L 的 [rule] 匹配本行

② 没命中任何 start：
     · 栈顶层的 end 命中 → 存档栈顶记录，栈顶出栈
     · 用栈顶的 [rule] 匹配本行；不匹配则依次向下（父层）尝试
```

**存档时机**：命中任意 start 时、命中 end 时、EOF 时。

### 3.2 层级与退出

子集合靠**父层的 start 命中自动退出**：

```
interface Eth-Trunk1     ← 命中 Interfaces.start，进入 Interfaces
 ip address 1.1.1.1 m    ← 命中 IpAddress.start，压入 IpAddress
 ip address 2.2.2.2 m    ← 又命中 IpAddress.start → 存档上一条 + 开新记录
 description X           ← 栈顶 IpAddress 不匹配 → 向下 Interfaces 匹配 ✓
interface Eth-Trunk2     ← 命中 Interfaces.start → 存档所有子层 + 回到 Interfaces
```

所以**大多数集合不需要写 `end`**。`end` 只在退出条件不是"下一个 start"时才需要
（如中兴的 `$` 块结束符、Nokia 的 `exit` 关键字）。

> ⚠️ **`end` 至今没有被任何真实模板使用过**（两份模板里 `end(` 出现 0 次），
> 更新（2026-11-21）：`end(^#$)` 已在华为 318 台全量验证；中兴的 `$` 分隔符也已加入引擎
> 裸分隔符清单并在 64 台真机上验证。诺基亚 `exit` 仍是唯一未实测的 end 形态。

### 3.3 关键事实：**作用域与文件排版无关**

这是本次评估最重要的实验结论，与文档旧版描述相反。

把同一份 16307 行华为配置做变形，用同一套模板跑，比对输出 JSON 的 MD5：

| 变形 | Interfaces | 输出哈希 | 与基线一致 |
|---|---|---|---|
| 基线（1 空格缩进） | 1044 | `2b304b066839` | — |
| **全部去缩进**（每行 lstrip） | 1044 | `2b304b066839` | ✅ **逐字节一致** |
| **接口子命令提到顶格** | 1044 | `2b304b066839` | ✅ **逐字节一致** |
| 全文统一 +4 空格 | — | — | ❌ 层级错乱，只剩 Device |
| 每行随机 0~8 空格 | 118 | — | ❌ 崩塌 |

**结论：运行期引擎完全不使用被解析文件的缩进。**

- 缩进只出现在两处：① **模板自身**的缩进（决定谁是谁的父）；② `start`/`end` 正则里作者自己写的 `^\s*` / `^`
- 运行期作用域由**状态栈**决定（"父帧还在栈上 → 子集合规则生效"）

**这意味着**：
- ✅ **Cisco IOS（无缩进、`!` 分隔）框架内可适配**——IOS 的接口块边界就是"下一个顶格 `interface` 行"，
  正好对应引擎"父 start 命中 → 存档所有子层"的语义。IOS 真正的难点是**90% 命令是全局的**（没有块），
  模板反而更简单。
- ⚠️ **JunOS（`{}` + `;`）需要一个新的作用域惯用法**——它的配置是扁平命令列表 + 点号路径，
  块边界不是退出关键字而是**路径前缀变了**。引擎没有"路径前缀作用域"这个概念，
  这是**唯一的真实语义缺口**。
- ✅ 中兴 M6000 与华为同为"缩进=层级"形态，额外有 `$` 块结束符与 `<!section>` 分区标记，两者都能映射到 `start`/`end`。

> **文档心智模型应改为「层级由模板声明，边界由正则触发」**——
> 按旧描述（"缩进 = 层级"），只读过文档的评审人会直接否掉 IOS/JunOS，而实际上 IOS 是能做的。

### 3.4 输出结构

**子集合的元素嵌在父元素的对应字段里**：

```json
{
  "Name": "Eth-Trunk1",
  "Mtu": 4474,
  "Description": "TO-[SNANK-PC-CMNET-RT01-NE5000E]-ETH-Trunk23=1*100GEUPLINKCR01",
  "IpAddress": [
    {"Address": "111.19.27.122",   "Mask": "255.255.255.252", "Family": "ipv4"},
    {"Address": "2409:8070:9A:1::702F", "Mask": "127",        "Family": "ipv6"},
    {"Address": "auto", "Mode": "link-local",                "Family": "ipv6"}
  ]
}
```

父子关系由**嵌套结构本身**表达 → **不需要 `inherit=`，也不需要在子集合里重复父层的 key**。

### 3.5 Key 聚合

**同一父元素下**，聚合键相同的子记录**合并成一个对象**，后到的补空缺、不覆盖已有：

```json
"BgpPeers": [
  { "Peer": "RR-L2", "Description": "...", "ConnectInterface": "LoopBack0" },
  { "Peer": "218.200.1.10", "AsNumber": 64650, "Group": "RR-L2" }
]
```

**键的构成**：集合内所有 `option(Key)` 字段值的**元组**。标一个 → 单字段键；标多个 → 复合键。

```text
Prefix      type(str) reg(\S+) desc(前缀) option(Key)
Mask        type(str) reg(\S+) desc(掩码) option(Key)
VpnInstance type(str) reg(\S+) desc(所属 VPN 实例) option(Key)
```

> 复合键的必要性：华为有两条路由前缀相同、掩码不同（`10.108.8.0/22` 与 `10.108.8.0/24`），
> 只按前缀聚合会把它俩并成一条。实测已确认该问题并用复合键修复。

**缺键的处理**：

| 情况 | 处理 |
|---|---|
| 全部 `option(Key)` 字段都为空 | 记录无法识别 → **丢弃** |
| 部分键字段为空（可选键，如上面的 VpnInstance） | 空值参与键计算，**不合并**也不丢弃 |

**顶层集合不做 Key 聚合**——Key 聚合的语义是「同一父元素下的子记录合并」，顶层没有父元素。
（Nokia 不同 router 下有大量同名接口，合并会直接吞数据。）

> 顶层集合的 `option(Key)` 字段仍然有意义：它是**扁平化时的外键来源**（见 6.5）。

### 3.6 Required 校验

标了 `option(Required)` 的字段缺失 → 该记录**无效，直接丢弃**。校验在记录存档时做。

### 3.7 嵌套 还是 独立顶层集合？

**判据：该命令是不是只出现在父层上下文里。**

| 情况 | 用哪种 | 实测 |
|---|---|---|
| 命令**只在**父块内出现 | **嵌套子集合** | 华为 `ip address` 529 条全在 interface 块内 |
| 命令在**多个上下文**出现 | 独立顶层集合 + `inherit=` | Nokia `port` 598 条里只有 43 条在 interface 块内 |

> ⚠️ **Nokia 这个推荐写法目前有坑**：`inherit=` 取的是"该集合该字段**上次**匹配到的值"，
> 不是"包含它的那一层"。实测 `interface IF1` 块**之后**出现的 `port 9/9/9` 会被归到 `IF1`。
> "上次见到" ≠ "所属"——Nokia 的 `port` 归属问题需要作用域模型增强，**单独排期**（见 7.2）。

### 3.8 引擎的几个必须知道的边界行为

写模板和消费输出的人都必须知道：

| 行为 | 实测 | 后果 |
|---|---|---|
| **`type(dict)` 父的子集合会塌陷成 dict** | `Bgp` 1 个 peer → `"BgpPeers": {...}`；2 个 → `[...]` | **同一份模板，输出结构随数据量变**。消费方不能假定子集合列一定是数组 |
| **无 `start` 的顶层集合只产出一条记录** | 3 条 port 规则 → 1 条（后写覆盖先写） | 要多条必须写 `start(...)` |
| **子集合无 `start` → 永不激活，产出 0 条且不报错** | 输出里整个键消失 | 静默丢数据，**lint 必须报"错误"** |
| **裸命名组不还原嵌套路径** | `(?P<Stat__Mode>\S+)` → 输出平铺列 `"Stat__Mode"` | 写嵌套字段要用 `${Stat.Mode}` |
| **`${X}` 与 `(?P<X>)` 同规则混用** | `redefinition of group name` 崩溃 | 二选一 |
| **类型转换失败静默保留原值** | `int` 字段拿到 `"notanumber"` → 输出字符串 | 需要 lint 提示 |
| **集合名 / 字段名重复静默覆盖** | 两个同名集合 → 记录混合 + 空记录 | lint 必须报错 |
| **正则语法错误运行时裸异常** | `PatternError`，不知哪条规则 | lint 必须编译全部规则 |

### 6.3a 块分隔符 `#` / `!` 参与 end 出栈（能力 B 全量复验时发现并修复）

**这是两个引擎级 bug，都来自「`#` 被当注释跳过」。** 全量 diff（8440 文件）暴露。

**bug 1 · `#` 早于 end 匹配被 continue 掉**

`probe_stack.py` 原逻辑：

```python
if st.startswith("#") and len(st) <= 2:
    continue      # ← 在 start/end 匹配之前就跳过
```

后果：模板声明的 `end(^#$)` **永远不生效**。`Acls` 从 `acl number 2000` 起
一路挂到几千行后的 `interface NULL0`，中间的 ` description SSH-Acl-Control`
被当成**接口**描述 —— **103 个文件的 NULL0 接口凭空多出 ACL 描述**。

修复（两层必须同时改，只改一层无效）：

| 层 | 改动 |
|---|---|
| 引擎 | 裸 `#` / `!`（长度 ≤ 2）参与 end 匹配，从最深一层起连同其上子层一起收起；未声明 `end` 的层不被关闭（向后兼容）；非裸 `#` 长行仍是注释 |
| 模板 | `Interfaces` / `VpnInstances` / `Acls` / `AclRules` 补 `end(^#$)` |

**bug 2 · 诊断器的两处误判（`tools/diff_incumbent.py`）**

| 误判 | 原因 | 后果 | 修法 |
|---|---|---|---|
| 字段声明判定 | `qualified in required` 子串包含：`RouteStatics.NextHop` 是 `RouteStatics.NextHopIface` 的子串 | 只声明 `NextHop` 的**修前**模板被判「已声明 NextHopIface」→ 真实的记录丢失错判成「字段已捕获」 | 按分隔符切分后精确匹配，裸名补集合前缀 |
| 缺口证据采集 | 对每列每文件无条件采证 | `VPN实例` 里两侧都正常捕获的 `ip binding vpn-instance __dcn_vpn__` 被当缺口证据，把整列拖成 `INSUFFICIENT` | 只在 `filled < incumbent.filled` 时采集 |

**验证**：全量 8440 文件，`接口描述` 多出 103 → **0**；接口数 6278430 **不变**，
8440/8440 文件接口数一致；19 列诊断**零 INSUFFICIENT**。
回归：`tests/test_engine_scope.py`（9 项）、`tests/test_diff_incumbent.py`（72 项）。

### 6.3b 缩进驱动层级（2026-11-20，模板审查轮）

**背景**：对 318 台真实配置（349 万行）做设计层审查，发现华为配置的层级
**完全由缩进表达**——纯缩进模型切出 441,180 块 / **0 异常**，缩进宽度只有
0/1/2、无 Tab、318 台 100% 一致。旧引擎的「一个 `#` 关整条嵌套块」与
`#` 自带缩进的事实冲突（`bas` 后紧跟缩进 1 的 `#` 占 95,887/96,006 次）。

**新增两个 opt-in 声明**（不写 = 旧行为，改引擎后重跑基线 +0.0，零回归）：

| 声明 | 语义 | 解决什么 |
|---|---|---|
| `indent(n)` | 本集合的**规则**只匹配「恰好 n 个前导空格」的行；**不约束 start 行**（视图入口属于父层级） | 同一条命令在两个缩进层出现且语义不同（`nas logic-port` 缩进 1 = 接口本级 / 缩进 2 = bas 视图正文） |
| `end_indent(n)` | 只有「恰好 n 个前导空格」的 `#` 才关闭本层 | `end(^#$)` 作用在原始行上，`^#$` 只锚第 0 列 → 缩进的 ` #` 匹配不上 → bas 层永不关闭、**2 万行丢失** |

**代价（必须知道）**：声明了 `indent(n)` 的模板，解析结果**依赖配置的缩进习惯**
——去缩进变形实验不再逐字节一致（接口数不变，但 `^ {n}` 规则全部失配）。
华为现网缩进 100% 一致所以安全；跨厂商模板不要照抄。
详见 `TEMPLATE-GUIDE.md` 8.6。

**同轮修掉的 6 个 bug**（5 个引擎 + 1 个模板侧，都真实影响输出，详见 `TEMPLATE-GUIDE.md` 8.3）：
start 行被缩进校验打回、子集合折叠用了父集合的 `coll.type`、
`-> A,B` 简写 `None` 覆盖真值、嵌套 list 字段被反复覆写、
模板空行重置 mode 吞规则。

### 6.3 安全基线（已实现，能力 A）

**现状**：脱敏已在引擎层落地（`type(secret)` + 密文形态兜底），全量 8440 文件
L1=68010 / L2=246 处被遮蔽，diff 报告零明文（`%^%#` 残留 0）。
下面保留原始问题描述与要求，作为该能力的背景记录。

**现状实测**：netparse 输出的 JSON 里含**完整可用的密文串**：

```json
"Password": "%^%#;}4v<YDuLCwX&[69w2WFv+ao8<R4O6_!Q*4ULlz:%^%#"
```

对应配置原文 `md5-password cipher 218.200.1.10 %^%#...%^%#`。

**要求**：
- 脱敏必须做在**引擎层**（`type(secret)` 或字段级 `secret()`），
  **不能做在资产层**——因为落盘的中间 JSON 也是明文
- 落盘产物一律脱敏，原始值只在内存里

### 6.4 扁平化输出（**延后**）

原计划支持 `--shape nested|flat`（子集合提升到顶层 + 注入外键）。**评估后建议延后**：

- 真实交付物是「一行一接口 + 1:N 折进列」的 xlsx 台账，**不是"每类资产一张表"**——flat 解决的是另一个产品形态的问题
- flat 会把**作用域错误固化成"看起来很权威的假外键"**：嵌套形状下"这条 port 属于哪个接口"至少还能看出是解析器猜的；
  扁平后它就是外键列里一个实打实的值，CMDB 会建出一条**假的关系**
- flat 的验收必须包含「**FK 值在父表里能唯一定位到一行**」的断言，孤儿检查查不出来（错挂的 FK 不为空）

设计细节见 6.5（保留备查）。

### 6.5 扁平化设计（备查，暂不实施）

若将来 CMDB 模型确认为「每类资产一张表」，按以下设计实施：

**外键命名（定稿）**：外键列名 = `<父集合名>_<父键字段名>`，**强制带父集合前缀**，永不与子集合自身字段撞名。

| 关系 | 外键列 | 值来源 |
|---|---|---|
| Interfaces → IpAddress | `Interfaces_Name` | 父记录的 `Name` |
| Acls → AclRules | `Acls_Number` | 父记录的 `Number` |
| Bgp → BgpPeers | `Bgp_AsNumber` | 父记录的 `AsNumber`（需显式声明，父无 `option(Key)`） |

**四个必须先解决的前置约束**：

1. **外键只能来自结构父**——顶层集合在 flat 里没有父记录，FK 无处可取
2. **`type(dict)` 父的子集合会塌陷成 dict**（见 3.8）——flat 必须同时处理 dict / list 两种形态
3. **FK 为空的语义**未定义（填 NULL 还是丢弃）
4. **表名全局唯一**——`as=<表名>` 声明的表名与"嵌套 list 字段提升后的表名"共享同一个顶层命名空间

**配套语法**：集合声明支持 `as=<表名>` 与 `fk(<集合>.<字段>)`（显式指定外键来源）。
> `fk(...)` 而不是 `parent(...)`——`inherit=` 已经存在且语义相反（"上次匹配到的值" vs "结构父"），
> 两个名字长得几乎一样会长期造成误读。模板语法一旦发布就是永久契约，改名成本此刻为 0。
